## 1. 背景与定位

### 1.1 为什么是 v0.84

v0.83.0 完成 Evidence Engine + Runtime API 后 ([project-v083-completion-state](../memory/project-v083-completion-state.md)), kernel-mapping §1.2/§2.4/§6 标 0-80% 的待办:

| 维度 | § | v0.83.0 完成度 | 缺失项 |
|---|---|---|---|
| Event Engine | §1.2 | 80% | Event Bus (0%) + EventLog retention (0%) |
| Event (统一输入) | §2.4 | 40% | Event 类型统一 (0%) + 5 种 event (0%) + Event Bus (0%) |
| Plugin SDK | §6 | 0% | web/api/ 4 端点直调 Engine, 违反 "Plugin 只产生 Event" 原则 |

per [project-strategy-kernel-first](../memory/project-strategy-kernel-first.md) Kernel-first 战略, v0.84 优先做底座, 不做应用层 (教师/家长/跨学科 extension 继续推迟到 Phase 7+).

### 1.2 战略选择: 底座三件套 + 1 endpoint demo

不只做 §1.2 三件套 (v0.82.x 推迟的), 顺手做 §6 的 1 endpoint demo. 原因:
1. **三件套单独完成 = "framework 准备好但没验证过"**: 不接 Plugin 等于没验证
2. **Plugin 改造必须等三件套就位**: 否则改 /api/answer 时 EventLog 没 retention / 没 Bus, 改完还要回头补
3. **1 endpoint 改造 = 风险可控**: 留 3 endpoint 给 v0.85, 不一次性大改

### 1.3 4-sub-commit 切分 (Bisen 拍板 2026-08-11)

保持 v0.80/0.81/0.82/0.83 节奏, 每 sub-commit 独立可测可回滚.

## 6. 3 个设计决策 (Bisen 拍板 2026-08-11)

### 6.1 CalibrationMessage → event_log 迁移策略

**决策**: **双写** (calibration_log + event_log)

**为什么不是单写**: 跟 v0.83.0-b Evidence 模式一致 (保留原 schema + 加新统一流). H3 ECE 验证脚本 + `update_calibration_actual_outcome` 仍在 calibration_log 读, 单写会破坏 v0.64.0 已落地的回写逻辑.

### 6.2 response_history → event_log 迁移策略

**决策**: **双写** (in-memory _response_history cap 100 + event_log)

**为什么不是单源**: in-memory cap 100 是 hot cache (FeatureExtractor 内部用), belief.py 读侧快. event_log 是 source of truth (跨进程/重启可重建). 双写跟 v0.81.0-b EventLog 模式一致 (in-memory + sqlite dual mode).

### 6.3 Plugin SDK 雏形 endpoint 选择

**决策**: **/api/answer** (POST 答题)

**为什么不是 /api/dual_agent**: dual_agent 路径复杂 (互校 orchestrator + CalibrationMessage), 跟 v0.84.0-a 双写联动, 改 dual_agent 等于同时验证 2 个 sub-commit, 风险叠加. /api/answer 是最常用路径, 改造成果明显 (Plugin 原则验证 + 端到端可视化), 风险中等.

## 7. 风险与不触发条件

### 7.1 触发条件 (满足任一即可启动 v0.84)

- ✅ v0.83.0 完成 (Evidence/Runtime 100%) - 已满足
- ✅ Kernel-first 战略 (Bisen 2026-08-06 拍板) - 已满足
- ✅ Plugin SDK 原则 (kernel-mapping §6 "Plugin 只产生 Event") 待落地 - v0.84.0-d 解决

### 7.2 不触发条件 (避免 v0.84 推迟)

- ❌ H3 验证失败: 无关 (v0.78 已通过, H3-c4 canary 仍跑)
- ❌ 现有架构不能稳定支持新功能: 无关 (v0.83 已稳定, 736 tests PASS)

### 7.3 风险点

| 风险 | 缓解 |
|---|---|
| /api/answer 改造 regression | v0.84.0-d 留 /api/judge / /api/dual_agent / /api/lca 给 v0.85, 一次只改 1 端点. +10 tests 覆盖 Plugin 路径 + backward-compat |
| CalibrationMessage 双写导致数据冗余 | calibration_log 是 dual_agent 详情 (calibration_round 等), event_log 是统一流. 两表 schema 不同, 数据不重复, 只是同一事件双持久化 |
| response_history 双写性能 | in-memory cap 100 是 hot cache, event_log 是 lazy append (async queue 留 Phase 7+). v0.84.0-c 加 retention 防无限增长 |
| EventBus singleton 状态污染 | kwargs 注入覆盖 + module-level reset helper + tests 强制隔离 |
