# v0.95+ 方向审查：验证滞后于抽象 + 应用层产品化规划（React 决策 + 学生端补全）

> **日期**: 2026-08-17
> **参与者**: Bisen + Claude (Mavis)
> **触发**: Bisen 提问 "v0.95 是应用（教师/家长端）？在 Kernel 底座基本具备之后，应用还是围绕 K12 学生吗？" -> 引发对 `research/deep-research/ECOS系统性深度分析-混合优化版.md` 全文 (1687 行) 的方向对照审查。
> **结论性质**: 方向审查 + 下一阶段规划 (无代码变更, 纯文档)

---

## 一、讨论背景

v0.94.0 (2026-08-13) 完成后, Kernel 侧 12 个深化版本 (v0.83 -> v0.94) 全部收口, 缺失清单 0, pytest 1365。Bisen 连续追问三个问题:

1. v0.95 应用层是否还是围绕 K12 学生?
2. 结合深度分析混合优化版, 项目方向是否有所偏移? 是否有必要重新审视?
3. Plugin SDK "100%" 意味着什么? 能否单独打包给其他项目? 应用端 UI 是否简陋粗糙?

## 二、核心结论

### 结论 1: 架构方向无偏移——混合优化版 2.0 蓝图被逐项兑现

文档第十部分 ECOS 2.0 蓝图 vs 实际落地对照:

| 文档蓝图 (混合优化版) | 实际落地 |
|---|---|
| §三 CTA 拆四层 (Observation -> FeatureExtractor -> Inference -> BeliefUpdate) | ✅ v0.80.0 完全同名 |
| §四 LCA 拆 Planner / ExperimentDesigner / Evaluator / PolicyLearner | ✅ v0.82.0 完全同名 |
| State Engine / Event Engine / Evidence Engine / Runtime API 6 个 | ✅ v0.80-v0.84 (replay/simulate/plan 都在) |
| §七 "Plugin 不调 Twin, 只产 Event" | ✅ v0.85 + v0.94, AST 扫描强制 0 mutation site (比文档建议更严格) |
| Goal 不应绑定 Bloom -> Goal Ontology | ✅ v0.86.0 |
| Policy 独立于 LLM、可学习可演化 | ✅ LinUCB -> Thompson -> POMDP + PBVI + T/R 在线后验 (v0.87-v0.93), 远超文档预期 ("Phase 5+ 升级 POMCP") |
| Twin -> Human Twin、教育 -> Multi-Domain【推演】 | ✅ v0.91 / v0.88 |

Kernel-first 战略 (Bisen 2026-08-06 拍板) 本质上就是文档第七部分 "Kernel 固化四项" + 第五部分三年路线第一阶段的执行。**这条线是收敛, 不是漂移。**

### 结论 2: 节奏有偏移——验证滞后于抽象（本次审查最重要的发现）

文档通篇最重的判断 (第五部分 §十二 + 总体结论):

> "ECOS 已经完成了'架构设计', 下一阶段应该完成'科学验证'。"

三个科学问题: ①Twin 是否准确? ②Policy 是否有效? ③是否具有长期增益?

对照现状:
- v0.80 -> v0.94 共 15 个版本、约 4 天, 全部投入 Kernel 深化与抽象推演 (pytest 736 -> 1365), 但三个科学问题的回答规模没有变化: **仍是 3 个测试用户 (lbc001/002/003)、1 门学科 (Python 基础)、LearningDNA 仍标"待启用"**。
- H3 通过 (v0.86 真 A/B 3-way) 是重要进展, 但仍是小样本。
- v0.88 Multi-Domain / v0.91 Human Twin 实现的是文档明确标注【推演】的分支 (通用认知运行时)。文档第九部分"自我修正"强调事实与推演的边界要保持——**现在的状态是: 推演在被工程化, 事实(教育场景验证)停在原地**。
- 文档第四部分三重护城河中, 最值钱的"数据护城河"(3 年+纵向认知数据) 在 Kernel 深化期间没有增长; 理论/工程护城河已接近饱和 (边际收益递减)。
- 文档第四部分四大短板只解决半个: ①无真实数据(未动) ②无 Evaluation 证据(Evaluation Engine 有了但没有真实数据喂) ③Behavior/Motivation(v0.87 部分补上) ④Product(v0.95 将落地)。

**审视结论: 不需要推翻方向, 需要做重心切换**——从"Kernel 深化/抽象推演"切换到"验证优先 + 单一垂直打通"。文档第九部分原话: "如果项目未来希望继续沿着教育方向发展, 建议保持目前定位, 不必刻意扩大边界。"

### 结论 3: "Plugin SDK 100%" 的确切含义——机制完备, 词汇表教育绑定

- **"100%" = 相对 v0.94 Kernel-only SDK 范围缺失清单为 0**: 契约 (Plugin ABC + PluginMetadata frozen)、注册 (PluginRegistry)、生命周期、持久化、文档、示例、测试全部齐备。今天为一个**学习场景**写 plugin, 全流程不需要再碰 Kernel 代码。
- **机制层领域无关** (形式通用): Plugin 不 import BeliefState、不持有 Runtime 引用、只进 event 出 result、AST 强制不 mutate state。
- **词汇表层教育绑定** (内容单一): ①可订阅 topic 被严格校验为 LearningEventType 10 值 + 1 内部 topic (全部学习事件), LearningEvent 带 student_id; ②可读状态面是 POMDPDiagnostic (Engaged/Frustrated/Bored/Confused 课堂 engagement 语义); ③3 个 first-party plugin 全是教学场景。
- **Multi-Domain 没有接到 Plugin 层**: v0.88 Domain ABC 影响的是 Kernel 内部 (plan_domain_aware / reward 调整), Event 词汇表和 Plugin 可读 state surface 完全没有 domain 参数化。
- **不可单独打包** (依赖闭包审查确认): `base.py` 硬 import `ecos.cta.event_log` (LearningEvent 是 on_event 签名类型); 2 个 first-party plugin import `ecos.lca.l4_optimization.pomdp_diagnostic`; pyproject 单一 ecos distribution 无子包。但 `PluginRegistry.subscribe_all(bus: Any)` 是刻意的 duck-typing 解耦, `PluginRegistryStore` 纯 stdlib——**挂载机制和持久化已可独立, 卡住的是事件契约和 first-party 内容**。
- **决策: 现在不抽独立 SDK**——等真实需求牵引 (第二个接入方或第二个领域落地时再抽, 那时半小时的事)。再抽是又一次"抽象先行于验证"。

### 结论 4: 应用端 UI 评估——粗糙, 且粗糙点卡在验证要害上

**技术层** (学生端 = 209 行 HTML + 891 行原生 JS + 558 行 CSS, 零框架零构建):
- 全局状态 2 个变量 (`let sid = '', q = null`), Phase 5 "App 对象统一状态管理" 债未还;
- 19 处 innerHTML 拼接 (XSS 面 + 无法组件复用的根因);
- API 地址硬编码 `http://localhost:5173`;
- 教师端 203 行, 数据是硬编码假数据 (S001/S002/S003 占位行), TeacherProgressPlugin 只输出到 `_log.info`, UI 完全没接。

**内容展示层** (真正的问题):
- 学生端信息密度不低, 但呈现方式是"给心理测量学家看的调试面板": θ/SE/confidence/post_liminal 术语直出, 无图表库;
- `web/api/interpretation.py` (364 行通俗化解读 API) 早已写好, 只部分接入;
- **UI 是 Evidence 的呈现面**: 深度分析文档第八部分核心论点是 Evidence 可解释性是"教师信任 Twin"的前提。教师端不把"为什么系统认为这个学生不会迁移"的证据链讲清楚, 教师就不会信, v0.95 验证目标就落空。**UI 粗糙 = 验证链路的一环, 不是装饰问题。**

**最重要的发现 (比 UI 粗糙更严重)**: v0.85 建好的 4 个行为事件端点 (`event_stub.py`: hint / idle / goal_change / reflection), 学生端 `app.js` **零调用**。即 v0.91 人类反馈轨迹、v0.92 行动历史、v0.94 HintFatiguePlugin, 整条"人的行为"数据通道在前端根本没有打开——**Kernel 侧全部就绪, 应用侧是断的**。接通这 4 个端点不需要等 React, 现有 app.js 加 4 个 fetch 即可, 是全项目性价比最高的单项任务 (同时开始积累 LearningDNA "≥50 题 + 交互行为数据"的启用条件)。

## 三、决策 (Bisen 拍板 2026-08-17)

### 决策 1: v0.95 起引入 React 完备前端架构

- **技术栈** (克制, 不过度工程化): React 18 + Vite + TypeScript + TanStack Query (服务端状态) + ECharts (图表) + context (客户端状态, 不引全局 store)。
- **理由**: ①三端(学生/教师/家长)三种受众共享组件 (5D 卡片/Bloom 雷达/证据链/演化图表), 原生 JS 三端规模必失控; ②证据链视图/POMDP 后验演化/成长轨迹是真正的可视化, 需要声明式渲染 + 图表库; ③Flask 本来就是纯 JSON API, 前后端分离成本最低的时机。
- **迁移顺序**: 教师端先行 (全新开发, 立架构抽组件) -> 学生端重写 (有真实用户, 不当试验场) -> 家长端 (纯复用)。
- **代价 (诚实)**: npm 构建链进 `check_defensive.sh` (tsc + eslint + vitest 最小集), pre-push 时长增加; 单人开发多一套工具链。必要成本, 必须进防御性自检体系, 不能成 CI 盲区。

### 决策 2: 学生端 UI 产品化改造升为主线任务之一

学生端的问题不是"样式旧", 是**产品定位错位**: 现在的界面是给系统开发者看的仪表盘, 不是给 K12 学生看的学习伙伴。四层改造:
1. **数据通道打通** (最高优先级, 不依赖 React): 接通 4 个行为事件端点, 解锁 v0.91-v0.94 全部 Kernel 投资;
2. **信息架构重设计** (学生视角三问): 我现在在哪 (通俗化层全接) / 我的成长 (Bloom 阶梯 + 5D 折线) / 下一步学什么 (目标可感知化);
3. **行为与动机层**: Motivation Profile (v0.87 Kernel 侧 100%) 前端零呈现, 应可感知化 (克制的成长反馈, 不做游戏化堆砌, 守"情感陪伴明确不做"边界);
4. **体验基础项**: 代码题编辑器升级 (CodeMirror)、移动端/平板适配、导出报告家长可读版。

### 决策 3: 抽象推演冻结, 验证欠债显式化

- Plugin SDK 独立打包 / Science-Career 事件词汇表 / Multi-Domain 落地: 只在真实需求牵引时启动;
- README + 12-kernel-mapping 增加"三个科学问题"跟踪表 (Twin 准确性 / Policy 有效性 / 长期增益), 像缺失清单一样维护——度量什么就会推进什么。

## 四、v0.95+ 任务规划 (修订版)

```
v0.95  前端产品化底座 + 教师端真实化
  a. React+Vite+TS+ECharts 底座, Flask API 不动, check 链扩前端段 (tsc/eslint/vitest)
  b. 教师端 API (/api/teacher/*) + UI 重写 (换掉假数据): 班级列表 + 学生详情
     (证据链视图 "系统为什么这么判断" + POMDP 诊断 + 干预历史)
  c. TeacherProgressPlugin 从 _log.info 升级为 UI 可消费
  d. (并行, 不等 React) 学生端 app.js 接通 4 个行为事件端点

v0.96  学生端产品化改造
  a. React 重写 + 信息架构三问 + interpretation 通俗化层全接
  b. 动机层呈现 + 答题体验 (CodeMirror) + 移动端适配

v0.97  家长端 (复用期, 成本最低) + 验证主线
  a. ParentEngagementPlugin 落地家长端 (engagement 演化 + 家校协同建议)
  b. 验证欠债显式化: 三问跟踪表进 README
  c. 小规模真实试点 (5-10 学生, lbc004+), 定义 H1/Twin 准确性数据收集方案
  d. LearningDNA 启用条件推进 (≥50 题)

v0.98+ (按需求牵引解锁, 不预先排期)
  - C/X 主导题扩量 (5 -> 20+)
  - Plugin SDK 独立打包 / Science domain 词汇表 (仅当第二个接入方/领域出现)
  - H1 形式化验证 (原设 50-100 学生, 视试点结果缩放)
```

关键依赖: "三问跟踪表"应立即做 (半天, 改变度量导向); v0.95a-c 是一条线; 试点依赖 v0.95/96 完成 (没有像样的教师/家长界面, 试点没有观察工具)。
