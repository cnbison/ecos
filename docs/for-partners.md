> **阅读对象**：有一定技术背景的校方项目合作负责人、教研技术骨干。

## 写在前面：三句诚实话

1. **这是一套可运行的原型系统，核心假设尚未经真实学生数据规模验证**——本文档会明确区分「已验证 / 待验证 / 先验值待校准」，不夸大。
2. **架构上它不是又一个「题库 + AI 问答」**，而是一个把「学生学到什么程度」建模为**可更新状态**、并据此做决策的系统（详见 §三、§四）。
3. **数据不出校**：系统可整套部署在学校本地，核心数据（学生的状态与答题轨迹）存校内 SQLite 文件（详见 §六）。

## 一、定位：从「阅卷机」到「状态追踪器」，技术版怎么说

传统系统（题库、刷题 App、阅卷系统）的技术本质是：**输入作答 → 判对错 → 按正确率挑选下一题**。它维护的是一个「正确率」标量，丢失了「为什么对/错」的过程信息。

ECOS 的技术本质是把这句话换掉：

> 把「学生学到什么程度」建模为一个**部分可观测的隐状态**（5D 信念分布），用**答题对错 + 学生自评**作为观测，持续做**贝叶斯后验更新**；再以更新后的状态为输入做**干预决策**；最后把状态与决策**以三种视角消费**（教师诊断 / 家长成长 / 学生进步）。

一句话：**领导版说的是「体检仪」，技术版说的是「对一个不可直接测量的隐变量做持续的概率推断」。** 这是它区别于「正确率驱动」方案的根本点。

## 二、总体架构

系统分四层，自下而上：

```
┌─────────────────────────────────────────────────────────────┐
│  应用层（React SPA）：教师端 / 学生端 / 家长端 三入口            │
├─────────────────────────────────────────────────────────────┤
│  Web API 层（Flask）：答题流 + 教师 7 端点 + 家长 2 端点       │
├─────────────────────────────────────────────────────────────┤
│  ecos 内核包（pip install ecos 可分发）                        │
│    · CTA 4 层：Observation→FeatureExtractor→Inference→        │
│                 BeliefUpdate（贝叶斯更新）                     │
│    · LCA 4 层：Planner→ExperimentDesigner→Evaluator→          │
│                 PolicyLearner（策略学习/决策）                 │
│    · 支撑模块：domain / goal / bloom / motivation /           │
│        event / evidence / evaluation / plugins / runtime      │
├─────────────────────────────────────────────────────────────┤
│  持久化层（SQLite，11 张核心表）                               │
└─────────────────────────────────────────────────────────────┘
```

要点：

- **内核与前端解耦**：`ecos` 是一个纯 Python 包，不带任何 UI 依赖，可独立安装、独立测试——这也是「本地部署」的技术前提（§六）。
- **Runtime 13 个 API** 把内核能力收口成一套稳定接口：`estimate / update_belief / replay / evaluate / simulate` ＋ `plan` 及 6 个 aware 变体（goal/motivation/domain/human_feedback/action）＋ `diagnose_pomdp / diagnose_pomdp_evolution`。前端只经 Web API → Runtime 这条路径访问内核，不直接触碰内部状态。
- **插件化可扩展**：Plugin SDK（抽象基类 + 注册表）已含 3 个第一方插件（提示疲劳 HintFatigue / 家长卷入 ParentEngagement / 教师进度 TeacherProgress），第三方能力（如对接学校自有规则）可按同一接口接入，不动内核。

## 三、认知状态模型：理论怎么落成数据结构

### 3.1 五个维度（5D Belief State）

系统对每个学生的核心状态是一个 `BeliefState`，含五个维度：

| 维度 | 英文 | 回答的问题 | 观测信号从哪里来 |
|---|---|---|---|
| K | Knowledge | 概念/事实记住没 | 客观题作答 |
| P | Procedure | 会不会按步骤做 | 程序性题目作答 |
| S | Strategy | 有没有思路、能否迁移 | 应用/分析层题目作答 |
| C | Confidence | 对自己会不会的把握 | **学生自评**（见 3.3） |
| X | External Support | 离开提示能否独立完成 | 提示使用量 |

**关键设计：每个维度不是单个分数，而是一个概率分布。** 数据结构上是：

- `theta_mean`：5D 联合均值向量（θ_K … θ_X）
- `theta_cov`：5×5 协方差矩阵（维度之间并非独立，如「知识」与「程序」相关）
- 每个维度派生 `mastery_prob`（掌握概率 ∈ [0,1]）与 `confidence`（系统对该估计的把握 ∈ [0,1]）

这样「两个 78 分」在系统里是**两个不同的分布**，而不是同一个数——一个可能 K 维集中、S 维分散，另一个相反。

### 3.2 Bloom 六层目标空间

「会」不是二元开关。借鉴布鲁姆认知目标分类，系统把每个知识点按六层挂接目标（Goal Ontology：Capability → Objective → Metric → Evidence）：

```
Remember 记忆 → Understand 理解 → Apply 应用 → Analyze 分析 → Evaluate 评价 → Create 创造
```

题目在**题库设计阶段**就标定了自己落在哪一层、考察哪个维度——这就是领导版说的「处方单」。判题后可据此定位「卡在哪一层」。

### 3.3 置信维度 C 的特别之处

「对错」无法区分「真会」与「蒙对」。系统在**揭晓对错之前**请学生自评「有几成把握」（4 档，pre-outcome），存入 `calibration_log`，用于标定置信维度。

> **诚实标注**：K/P/S/X 四维由客观答题驱动贝叶斯更新；C 维目前通过自评数据做**离线校准**。把「自评折扣真实掌握」（confidence_for → 信念更新）这一步**尚未接入在线流程**，计划等试点数据回来后一并校准（避免在无数据时拍脑袋定权重）。

### 3.4 可追溯：判断依据落地

`BeliefUpdate` 每次更新状态时，同步写入 `evidence_log`（每个维度一行，携带 `dim` 标记 + 判断依据），并把「发生了什么」写入 `event_log`（两类事件：`response_submitted` 作答 + `observation` 观测）。意味着**任何一条「这孩子知识维度偏弱」都能回溯到「依据哪几题的哪几次作答」**——这是系统对教师端「证据卡」的支撑，也是「可被审计」的技术保证。

## 四、「一道题」的完整数据流（技术版）

对照领导版六步，逐步标注触发的模块与落库：

| 步 | 业务动作 | 触发模块 | 输入 | 写出 / 更新 |
|---|---|---|---|---|
| 1 | 学生做题 | `/api/question` 选题（Goal 驱动） | 学生 ID | 题目（含 dim + bloom 标注） |
| 2 | 学生自评信心 | 前端采集（pre-outcome） | 4 档自评 | `calibration_log` |
| 3 | AI 判题 | `/api/judge`（LLM + 过程分析） | 作答 | 对错 + 过程判断 |
| 4 | 更新认知状态 | `/api/answer` → CTA `BeliefUpdate`（贝叶斯） | 对错 + 自评 | 内存 `BeliefState` ＋ `evidence_log`(5 行) ＋ `event_log`(2 行) |
| 5 | 决定怎么帮 | LCA `Planner`/`PolicyLearner`（POMDP policy） | 最新状态 | `interventions`（干预建议） |
| 6 | 三端呈现 | 教师/家长/学生 Web API | 状态 + 干预 | 三份视图 |

其中第 4–5 步是内核核心：

- **第 4 步（CTA）**：`Inference` 层做后验更新——给定先验分布（上一步的 `theta`）与新观测（对错/自评），用贝叶斯规则推得新分布。分布而非点值的好处：**没把握时它会保持「不确定」，而不会武断地跳**。
- **第 5 步（LCA）**：决策并不「看着正确率」拍板，而在 POMDP 框架下权衡（详见 §五）。

## 五、几个关键机制的技术说明

### 5.1 双 Agent 互校（CTA ↔ LCA）

CTA「诊断」与 LCA「开方」不是单向流水线，而是闭环互校：LCA 每次「开方」前，CTA「复诊」；一个模块的判断没把握时，不擅自下结论。

- 实现上有独立的**反幻觉检查**（`belief_check`，对 5D 逐个维度校验估计是否越界/自洽）；
- 双 Agent 之间走**协议状态机**（如 `strategy_challenge`「策略质疑中」）——一方可挑战另一方的结论。

价值：把「AI 想当然」的典型失败模式，从「信任模型」改成「机制上互相牵制」。

### 5.2 为什么要 POMDP：处理「不可观测」

「学生是否真正掌握」是**不可直接观测**的——我们只能看到答题对错、自评、用时这些**观测**，观测是隐状态的有噪反映。POMDP 正是刻画这一点的数学框架：

- 隐状态 = 学生的认知/投入状态；观测 = 作答与自评；
- 系统维护隐状态的后验分布，用观测逐步更新（T/R 后验，Beta-Multinomial 共轭后验 + 后验均值接入 point-based 求解器 PBVI）；
- 决策目标 = 在「不确定」下最大化长期学习增益（而非「短期答对率」）。

### 5.3 记忆衰减与间隔复习

人学过的知识会遗忘（艾宾浩斯曲线）。系统据此把「何时复习」纳入决策：`planner` 接线了间隔复习（Bjork spacing）与脚手架调节（ca_scaffolding），决定「该不该现在复习、给多少提示」。

### 5.4 认知孪生（Cognitive Twin）

长期来看，系统维护的不仅是一份状态，而是一个「孪生」——三元组/四元组：**信念状态 + 学习轨迹 + 人类反馈 + 行为历史**。这是「持续 6–12 年陪伴、越用越懂一个学生」的技术载体，也是项目 3 年数据护城河的来源。

## 六、部署与对接（本地部署技术方案）

### 6.1 组件与硬件要求

系统部署形态为**单机 / 内网服务**，组件简单：

| 组件 | 说明 |
|---|---|
| Web 服务 | Python 3.11+ + Flask，托管后端 API 与编译好的前端静态文件 |
| 前端 | React 18 + Vite 6 + TypeScript，构建产物为一堆静态文件 |
| 数据 | SQLite 单文件数据库（11 张核心表），无需独立数据库服务器 |
| 外部依赖 | LLM 判题走云 API（当前适配 MiniMax / Moonshot），可配置切换 |

> 无 GPU 要求、无独立数据库/缓存中间件要求；一个内网服务器或虚拟机即可承载，数据以本地 SQLite 文件形式留存，备份 = 复制文件。

### 6.2 与学校现有系统的对接边界

| 事项 | 现状 | 需要学校侧配合的点 |
|---|---|---|
| 学生名单 | 可从 DB 直接导入 | 提供脱敏后的名单格式约定 |
| 账号体系 | demo 为「知道 student_id 即可访问」（无鉴权） | **需对接单点登录/统一身份**（正式部署前必做） |
| 题库 | 内置示范题库（带 dim + bloom 标注） | 学校自有题库需按「处方单」规范补充标注（见 6.3） |
| 教务数据 | 尚未对接 | 按需评估 |

### 6.3 数据安全与外部 AI 调用

- 学生的状态、答题轨迹等**核心数据存校内**、不上传云端。
- 唯一的外部调用是 **AI 判题**（提交作答文本给云 LLM 取回判断）。如需彻底「不出校」，可评估**替换为本地模型**；当前架构上判题为一个独立环节，可被替换而不影响内核。
- 若走云 LLM，数据发送前可做脱敏处理（学生用编号、不含姓名等身份信息）。

## 八、验证方案（技术化）

试点验证聚焦两个核心假设，方法如下：

### H1 — 状态追踪的预测效度

「5D 状态是否真的能预测学生后续表现？」

- **指标**：用状态推导的 `expected_accuracy` 预测下一题对错，统计：
  - 校准度 ECE（Expected Calibration Error，10-bin）；
  - 判别力 AUC；
- **证伪线**：≥100 题后 ECE 仍 > 0.25 且无下降趋势，或 AUC ≤ 0.55。

### H1-T — Twin 判断与人类判断的一致性

「系统对『学生投入/受挫/无聊/困惑』的判断，与教师/家长的判断是否一致？」

- **指标**：系统 POMDP `most_likely_state` vs 人工 4 档标注，算 Cohen's κ；
- **证伪线**：κ ≤ 0.2（slight agreement 以下）持续 2 个评测周期。

### 采集方案

- 规模：5–10 名学生（全新编号，不复用历史数据），4 周，每生 ≥50 题；
- 自动采集：答题流已接通 `evidence_log` / `event_log` / `calibration_log`，零人工；
- 人工采集：每周 15 分钟教师/家长 4 档标注（对照 Twin 判断），学生用编号不记姓名。

## 十、FAQ（技术向）

**Q：部署大概什么量级？**
A：单机/内网即可，无 GPU、无独立数据库。一个 Flask 进程 + 一份 SQLite 文件 + 一份前端静态文件。规模到全校级（数千学生、每日几十万答题）时需评估 SQLite → PostgreSQL 迁移，内核层已隔离持久化接口，迁移不动业务代码。

**Q：能不能对接我们现有的题库？**
A：技术上可以，前提是题目补上「处方单」标注（考察哪个维度 K/P/S/C/X、哪个 Bloom 层级）。这需要学科老师配合标注，或未来提供标注工具辅助。内置示范题库可直接跑通流程。

**Q：只有 AI 判题需要联网，能不能完全离线？**
A：判题环节是独立可替换的。若要求彻底离线，可将云 LLM 替换为本地模型或确定性判分（客观题）。内核的状态追踪不依赖外部 AI。

**Q：系统怎么保证「判断可解释」？**
A：每条状态更新都带 evidence（判断依据），教师端可下钻到具体题目与证据。代码级的可解释性由「分布而非黑箱点值 + 证据可回溯」保证；不是「给一个分数」而是「给一个分布 + 依据」。

**Q：怎么扩展新能力？**
A：经 Plugin SDK 接入，不触碰内核。已有的三个第一方插件即为样例。

## 结语

这份文档想传递的最关键信息是：**ECOS 不是「又一个更强的人工智能题库」，而是一个把「理解学生」这件事系统化、可验证、可追溯的尝试**。

对合作负责人而言，值得关注的不是「它现在有多准」（这恰是待验证的），而是——

1. **架构是否有长期演进的余地**（状态内核 + 插件化 + 持久化隔离，答案是「有」）；
2. **数据是否安全可控**（本地部署、核心数据不出校，答案是「是」）；
3. **验证是否诚实、可执行**（H1/Twin 有明确的指标与证伪线，答案是「是」）。

若学校愿意以「试点」方式小规模、低成本地一起验证第 8 节的两个假设 —— 那正是我们当前最需要的合作方式。
